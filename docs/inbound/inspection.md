# 검수

<div class="page-meta"><span>입고</span><span>실물 확정</span><span>10분</span></div>

검수는 입고 주문과 실제 상품을 비교해 재고로 편입할 SKU·수량·LOT·유효기간과 품질 상태를 확정하는 공정이다.


## 검수 흐름

<div class="flow-strip"><span>작업 상품 선택</span><i>→</i><span>상품 식별</span><i>→</i><span>수량 확인</span><i>→</i><span>LOT·유효기간</span><i>→</i><span>상태·상세 검수</span><i>→</i><span>정상·예외 분리</span></div>

## 검수 항목

| 항목 | 확인 내용 | 소유 도메인 |
|---|---|---|
| 상품 식별 | SKU·바코드·UOM | 상품 |
| 물류 정보 | 체적·중량·취급 이미지 | 상품 |
| 수량 | 예정·실제·누적·잔여 | 입고 |
| 재고 속성 | LOT·유효기간·시리얼 | 재고 |
| 품질 | 정상·파손·오염·불일치 | 입고 예외 |

검수 화면에서 상품 정보가 부족하면 UOM·체적·중량·이미지 보완 화면으로 이동한다. 하지만 해당 정보의 소유자는 상품 도메인이며 입고 작업마다 새 값을 만드는 것은 아니다.

### 상품 정보 보완 화면 분기

::: info 현재 CGKR AS-IS
백엔드는 상품 UOM의 길이·너비·높이·중량·체적 중 하나라도 0 이하이면 보완 대상으로 표시한다. 프론트는 이 표시 또는 첫 상품 이미지가 `null`인지를 확인해 검수 수량 입력 전에 상품정보 화면으로 이동한다.
:::

```text
상품 스캔
→ UOM 치수·중량·체적 확인
→ 상품 이미지 확인
├─ 정보 충분: 검수 수량 입력
└─ 정보 부족: 상품정보 보완 화면
   ├─ 저장
   └─ Skip으로 다음 단계 진행 가능
```

현재 상품정보와 이미지 화면에는 Skip 동작이 있어 보완 화면으로 이동하는 것과 입력 완료가 필수인 것은 다르다.

## 수량

```text
검수 가능 수량
= 주문 예정 수량 - 누적 정상 수량 - 예외 점유 수량 - 종결 수량
```

여러 작업자가 처리할 수 있으므로 화면 진입 시점뿐 아니라 제출 시점에도 잔여 수량을 다시 검증한다.

### 예정·실수량 허용 범위

CGKR은 분할되지 않은 검수 행에서 실수량이 예정수량의 ±10% 범위이면 정상 진행 상태로 처리하고, 범위를 벗어나면 예외 상태로 분리한다.

```text
정상 최소수량 = ceil(예정수량 × 0.9)
정상 최대수량 = floor(예정수량 × 1.1)

정상 최소수량 ≤ 실수량 ≤ 정상 최대수량 → 정상 진행(PROC)
그 외                                 → 예외(EXCP)
```

예정수량이 100EA라면 90~110EA는 정상 진행 범위이고, 89EA 이하 또는 111EA 이상은 예외다.

::: warning LOT·유효기간 분할 시 현재 처리
LOT·유효기간에 따라 여러 행으로 분할되면 각 분할 행의 계획수량을 해당 행의 실수량으로 다시 설정한 뒤 판정한다. 이 경우 개별 분할 행은 ±10% 판정을 사실상 통과할 수 있으므로, 원래 예정수량과 모든 분할 행의 합계도 별도로 대사한다.
:::

## LOT·유효기간

| LOT 관리 | 유효기간 관리 | 입력 |
|---:|---:|---|
| Y | Y | LOT·유효기간별 수량 |
| Y | N | LOT별 수량 |
| N | Y | 유효기간별 수량 |
| N | N | 수량만 확정 |

세부 행의 수량 합은 검수 수량과 일치해야 한다. 같은 SKU라도 LOT·유효기간·입고회차가 다르면 별도 SKU Instance가 된다.

## 상세 검수

품질 지시가 있는 상품은 작업 설명과 참고 사진을 기준으로 실물을 비교한다. 이상 판정에는 사유와 수량을 기록하고 정상 수량과 분리한다.

## Pallet·취급 단위

검수 과정에서 Pallet·재포장 등 작업 유형과 부자재·횟수를 기록할 수 있다. 이는 작업 이력이며 Inventory 수량을 증가시키는 사건은 아니다.

## 검수 결과

```text
검수 결과
├─ 정상 수량 → 입고 작업·적치 대상
└─ 예외 수량 → 입고 예외 판정
```

## 임시 적치 관계가 있는 상품

::: warning 현재 CGKR AS-IS 용어 주의
백엔드는 상품에 활성 임시 적치 관계가 하나라도 존재하면 별도 플래그를 `Y`로 반환한다. 이는 최종 Location 적치완료를 뜻하지 않는다.
:::

프론트는 이 플래그를 가장 먼저 확인해 상품 상태가 `REQR`·`PROC`인지 검사하기 전에 라벨 화면으로 이동한다. 코드 주석은 이를 “입고 완료된 상품”이라고 표현하지만 실제 판정 기준은 임시 적치 관계의 존재다.

```text
상품 스캔
→ 활성 임시 적치 관계 확인
├─ 존재: 라벨 화면으로 이동
└─ 없음: REQR·PROC 여부와 예외·상품정보 조건 확인
```

따라서 화면의 “이미 처리된 상품”과 최종 피킹로케이션·보관로케이션 적치완료를 같은 의미로 해석하면 안 된다.

## 상품 단위 검수 취소(`ZERO`)

::: info 현재 CGKR AS-IS
이 절은 Confluence 공식 정책을 새로 정의한 것이 아니라 현재 `cgkr_ui`와 `cgkr_app`에서 확인한 상품 단위 취소 동작이다. 정책 변경과 최종 승인은 Confluence 원문을 기준으로 한다.
:::

검수 화면에서 상품을 취소하면 상품 수량을 `0`으로 수정하지 않고 취소한 입고 상품의 처리 상태만 `ZERO`로 변경한다. `ZERO`는 입고 신청 전체를 취소하는 `CNCL`과 다른 상품 단위의 종결 상태다.

```text
상품 취소 확인
→ POST /inbound/set-zero
→ 진행 중인 임시 Location 작업 존재 여부 확인
├─ 존재: 취소 차단
└─ 없음: 상품 상세 상태를 ZERO로 변경
   → 취소 전 REQR·PROC 상품 수 확인
      ├─ 1개: POST /inbound/complete로 전체 입고 상태 재계산
      └─ 2개 이상: 남은 상품 검수 계속, 입고 전체 상태 유지
```

### 마지막 처리 가능 상품 취소

프론트는 취소 전에 `REQR`·`PROC` 상태인 상품을 센다. 취소 대상이 마지막 한 건이면 `set-zero` 성공 후 `complete`를 호출한다. 백엔드는 이때 특정 상품만 보지 않고 같은 입고에 포함된 모든 유효 상품의 상태를 다시 집계한다.

| 전체 상품 상태 조합 | 입고 전체 상태 | 의미 |
|---|---|---|
| 전부 `ZERO` | `DONE` | 처리할 상품이 없어 입고완료 |
| `DONE + ZERO` | `DONE` | 완료·취소된 상품만 남음 |
| `STOW + ZERO` | `STOW` | 적치·보관대기 상품이 남음 |
| `DONE + STOW + ZERO` | `STOW` | 일부 적치 단계가 남음 |
| `REQR`·`PROC` 포함 | 변경 없음 | 남은 상품 검수 계속 |
| `EXCP` 포함 | 현재 집계 분기 없음 | 완료 판정 검증 필요 |

`REQR`·`PROC` 상품이 남은 경우 백엔드가 입고 전체를 새 상태로 바꾸는 것이 아니다. 기존 입고 상태가 보통 `PROC`이므로 그대로 유지된다. 입고 `PROC`의 명칭은 `상품검수중`이며, `상품준비중`은 출고 `PICK` 상태의 명칭이다.

### 현재 구현상 주의점

- `set-zero`와 `complete`는 별도 API·트랜잭션이므로 첫 호출 성공 후 완료 호출이 실패할 수 있다.
- 두 작업자가 마지막 두 상품을 동시에 취소하면 둘 다 완료 호출을 생략해 모든 상품이 `ZERO`인데 입고 전체 상태가 `PROC`에 남을 수 있다.
- 프론트는 `EXCP`를 처리 완료 상태로 보지만 백엔드 완료 집계는 `EXCP`를 세지 않아 상태 재계산이 조용히 생략될 수 있다.
- `set-zero` 백엔드는 현재 상품 상태·화주 소유권을 조건으로 갱신하지 않고 상품 식별자만으로 상태를 변경한다.
- 백엔드에는 `ZERO` 조합과 동시 취소를 검증하는 전용 테스트가 현재 확인되지 않는다.
- 상품정보 화면은 체적을 `CUFT`로 표시하면서 치수 곱을 그대로 전송하고, 중량은 `KG`로 표시하면서 입력값을 1,000배 해 저장 경로로 보낸다. 화면 단위와 저장 수치의 정합성 검증이 필요하다.

## 정책

1. 입고 주문 상품과 실제 SKU를 연결한다.
2. 예정 수량과 실제 수량을 별도로 보존한다.
3. LOT·유효기간 관리 상품은 해당 값을 필수로 확정한다.
4. 세부 재고 속성별 수량 합을 검수 수량과 맞춘다.
5. 예정수량의 ±10%를 벗어난 실수량은 정상 처리하지 않고 입고 예외로 분리한다.
6. 상품 정보 보완과 검수 실적 변경을 같은 사건으로 처리하지 않는다.
7. 이상 수량·사유·사진·작업자를 기록한다.
8. 정상 검수 수량만 입고 작업과 적치 대상으로 전달한다.
9. LOT·유효기간 분할 행의 합계와 원래 예정수량의 차이를 별도로 확인한다.
10. 상품 단위 취소는 수량을 덮어쓰지 않고 해당 상품 상태를 `ZERO`로 기록한다.
11. `ZERO`는 입고 신청 전체 취소 `CNCL`과 구분한다.
12. 마지막 처리 가능 상품 취소 후에는 전체 입고 상품 상태를 다시 집계한다.
13. `REQR`·`PROC` 상품이 남아 있으면 입고 전체 상태를 완료로 변경하지 않는다.
14. 치수·중량·체적 또는 이미지 정보가 부족하면 상품정보 보완 화면으로 안내한다.
15. 상품정보 보완 화면의 Skip 허용 여부와 실제 필수 입력 정책을 구분한다.
16. 임시 적치 관계 존재를 최종 Location 적치완료로 해석하지 않는다.
17. `EXCP`를 화면 완료 상태로 판단하는 규칙과 백엔드 전체 상태 계산의 차이를 별도 검증한다.
